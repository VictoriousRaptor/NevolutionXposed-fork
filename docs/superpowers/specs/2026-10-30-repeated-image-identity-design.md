# 重复图片通知的精确消息关联

## 意图与约束

修复重复发送完全相同图片时，旧消息身份重新进入观察窗口、使当前图片通知无法唯一选择事件的问题。消息身份必须独立于图片内容和文件路径；不同会话、不同消息不得因图片相同而合并。没有手机，本轮只做离线验证和签名构建。

## 方案

采用现有通知身份链路：`WeChatRecallEvents` 在已校验的 `NotificationItem.a(Context)` BEFORE 回调中写入会话、服务器消息 ID 和核验标记；图片事件已经保存同一服务器 ID。图片请求在通知归一化前固定这组身份，按会话和服务器 ID 选择图片事件，不再让其他消息的身份与它竞争。

仅按时间排除旧身份会在通知时间滞后时串图，因此不采用。按图片哈希或共享路径合并会丢失消息边界，也不采用。本次复用既有元数据，不增加 hook、混淆映射、下载能力、设置或依赖。

## 行为

- 只有核验标记、非空会话和正数服务器 ID 同时存在，才使用精确关联。
- 有精确身份时，会话不符、目标未出现或多条事件声称同一 ID 均拒选；目标身份先到、路径后到时沿用等待和重试，不退回选另一张图片。
- 没有精确身份时，保留原时间/观察窗口及歧义拒选。
- 两次通知即使正文、时间和图片文件相同，只要精确身份不同就不得复用旧请求。
- 后续文字通知继续按原图片请求的身份和既有 token、消息前缀规则判断图片连续性。
- 索引容量、30 秒 TTL、等待预算、已分配事件限制、撤回清理与图片呈现保持原有约束。
- 图片与占位互斥只作用于展开 RemoteViews 的克隆：精确定位对应 incoming 占位后清空其渲染文本，原始 transcript 与回复数据保持不变；图片/模板/身份不可用时只显示原占位。
- 对有图片请求 token 且有 incoming 占位的待图 RemoteViews 设置并验证 `FLAG_REAPPLY_DISALLOWED`（token 只由开启图片预览时创建）。AOSP SystemUI 只查看旧 RemoteViews 的 flag，因此必须从待图阶段开始标记；已有无 flag 旧缓存或待图 inflate 被更新取消时，首次过渡仍未保证。运行时接口不可用时保留占位、不显示补图。
- 对连续的后续文字通知安排有界重检，覆盖图片先发布、原通知后提交的短窗口；仍以请求实例、token 和消息前缀为边界。不持有 loader 锁调用通知服务。

## 验证

主机回归覆盖重复路径不同消息 ID、多个旧身份、通知时间滞后、目标路径迟到、精确目标缺失、同 ID 冲突、跨会话、TTL 和无核验身份的回退。Android framework 用例覆盖 render-only 占位替换、原文保留、RemoteViews 重绑标记和 later-text 身份保留；用例编译不等于真实 SystemUI 动画或通知提交顺序验收。运行完整 Debug 主机测试，完成规定的签名 Debug 构建、Release 构建及 lint 并核对证书；运行时 hook 安装和真实微信/SystemUI/OEM 行为均待设备验证。
