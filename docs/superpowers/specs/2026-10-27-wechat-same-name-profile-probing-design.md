# 同版本名微信构建的运行时画像探测设计

日期：2026-10-27

实现同步：2026-11-02。初始目标 3183 现已有 APK 离线证据和精确画像；当前版本与验证边界以[适配手册](../../wechat-version-adaptation-playbook.md)及[8.0.79 记录](../../wechat-8.0.79-findings.md)为准。下文缓存通道已同步为最终实现，历史 provider/广播/服务方案不再保留。

## 意图

当微信的 Android `versionName` 与已有画像相同、`versionCode` 却未列入白名单时，模块在微信主进程启动时逐功能探测同名画像。完整运行时签名唯一匹配后，自动启用该功能，并明确记录这是未经目标 APK 语义核对的实验性兼容。首个目标是 8.0.79/3183；规则适用于所有已有 `versionName` 的新 `versionCode`。

## 目标与边界

- 精确的已核对 `versionName && versionCode` 组合保持原有优先级和行为。通知栏回复现有 8.0.72/8.0.78 的名称或代码任一匹配，以及其他未命中组合的 legacy 回退也保持；新增规则不扩大这些历史回退。
- 未知 `versionCode` 只尝试**同一 `versionName`** 的已知画像；各功能独立判断，不借用别的功能的结果。8.0.77 的 3141/3160 等多画像版本须唯一匹配。
- 通知栏合成回复、图片事件、普通大图下载、应用内回复事件、撤回身份/事件、通知原生 Emoji 保留分别探测。维持各自现有开关、作用进程和失败回退；没有该功能的同名画像时不推断支持。
- 探测只解析类、方法、字段、继承及必要的 static/abstract 属性，不在探测阶段发送回复、查询或下载图片、修改通知、触发撤回，也不为了“试挂”先安装 hook。
- 通过探测不等于方法语义、数据库列含义或真实设备行为已验证。诊断和文档必须称为“实验性签名匹配”，不得称为目标构建已适配或真机验收通过。
- 不对未知 `versionName` 扫描全部微信类、猜测混淆名或新增跨版本名匹配。通知原生 `PendingIntent` 回复和不依赖微信混淆画像的 framework 外观路径沿用现状。

## 已考虑的方案

| 方案 | 得益 | 代价与决定 |
| --- | --- | --- |
| 继续只接受精确组合 | 兼容结论最保守 | 3183 等同名新构建无法自动使用已有功能；不选。 |
| **同名候选逐功能完整签名探测，唯一命中后自动启用** | 满足用户对所有同名新构建的要求，并限制候选范围 | 签名不能证明语义相同，须明确实验性、隔离失败并保留回退；选用。 |
| 不限版本名或按相近 `versionCode` 猜画像 | 可能覆盖更多构建 | 混淆布局与字段语义易误判，无法明确回退边界；不选。 |

## 选择与安装

1. 在现有微信主进程 `Application.onCreate(): void` AFTER 初始化流程中取得安装包身份：`versionName`、长 `versionCode`、`lastUpdateTime`，以及模块画像格式版本。已知精确组合直接取原画像。只有同名且未知代码才进入实验性候选探测。
2. 各功能只遍历其同名候选。预检完整依赖图：目标类、继承关系、方法参数和返回类型、实例/static/abstract 属性、字段名称与类型，以及该功能现有的其他约束。合成回复额外要求接收器、RemoteInput 辅助方法及所有车载门禁均通过；Emoji 仍须取消已核对直接调用者的优化成功才激活。图片事件和下载服务分别判定。
3. 恰有一个候选完全通过时返回该功能的实验性画像；零个或多个通过都保守回退，并记录 `no_match` 或 `ambiguous`。已知精确组合不受同名候选歧义影响。通知栏回复未命中时保留现有 legacy 候选及其签名校验，不把 legacy 结果记录成新构建画像。
4. 预检通过后才安装 hook。每个功能的回调在全部必需 hook 安装完成前保持不活跃；任一安装失败须撤销已安装句柄或令其保持不活跃，并只关闭该功能。合成回复的车载门禁必须全部成功，不能部分安装后仍报告可用。原生回复路径不受实验性合成路径失败影响。
5. 保持现有开关时机：图片预览关闭时不安装图片事件或大图 hook；普通大图还须大图开关开启。Emoji 为支持微信进程运行期间直接切换设置，启动时即探测并安装合格 hook，回调每次读取微信通知增强及 Emoji 开关，默认不改变文本。候选探测不绕过任何功能开关。每个微信进程内至多做一次完整候选枚举；通知处理时不重新探测。

## 缓存与失效

- 持久缓存只存各功能**唯一命中的候选标识**，不存 `Class`、`Method`、`Field`、hook 句柄或“行为已验证”结论。键包含功能、`versionName`、长 `versionCode`、微信 `lastUpdateTime` 和模块画像格式版本。libxposed API 102 的远程偏好只读，实机 provider 不可达、广播/服务通道也未成功，因此最终由微信主进程在应用自身私有存储的独立 `wechat_profile_candidates` 偏好组同步保存画像 ID，与模块用户设置分离。模块侧 provider、广播和服务缓存通道均已移除。2026-10-29 的 3200 Emoji 候选曾完成跨微信进程启动的持久化与完整签名重检；这一结果不能推断到其他功能或真实消息行为。
- 同一安装构建再次启动微信时，先读取候选标识，仍在新进程的 ClassLoader 中快速复核完整签名，再重新安装 hook。验证失败则丢弃该缓存并重新枚举同名候选。微信更新、模块画像变更或安装时间变化均使缓存失效。
- 零命中和歧义只在当前进程内记住；下次微信启动可重试，避免类加载时机造成永久误判。缓存写入失败不妨碍本次有效的运行时探测与安装，但不能声称实现了“同一安装构建只做一次完整候选枚举”；交付前须修复缓存写入路径。

## 诊断、测试和交付边界

- 日志只记 `versionName/versionCode`、功能名、选中画像标签、`exact`/`experimental`、失败阶段及异常类型；不记消息内容、联系人、设备标识或 APK 本机绝对路径。`ready` 只表示 hook 安装，不代表消息收发、图片下载、撤回裁剪或 Emoji 显示正确。
- 主机测试覆盖精确组合优先、8.0.79/3183 同名唯一命中、8.0.77 多候选唯一/歧义/零命中、跨版本名拒绝、每项功能独立失败、缓存命中与失效、安装中途失败后的惰性回调/清理、已有开关与 legacy 回退。尽可能用合成类验证完整签名，不把测试夹具当成 3183 APK 证据。
- 同次代码变更更新 `docs/wechat-version-adaptation-playbook.md` 与受影响的 `docs/wechat-<版本>-findings.md`、Emoji/图片/回复专题文档，分别写清匹配语义、完整签名、开关、进程、失败行为和诊断。初始设计时 3183 无 APK；现已取得 APK，其来源、SHA-256、原始描述符与各层验证结果见上述当前文档。其他未取得 APK 的新构建仍记录证据缺口，不捏造反编译结果。
- Debug APK 若用于交付，按仓库规则以现有 release 证书签名并核对证书。此次设计不授权安装 APK、重启微信或设备、推送或发布。

## 实施者可决定的细节

- 在不改变上述匹配与失败语义的前提下，提取共用探测器和缓存代码的具体类名及内部 API。
- 缓存入口固定使用微信应用自身的独立候选偏好组；后续调整须重新验证写入和跨进程启动重检，不恢复已移除的 IPC 作为未经验证的回退。
