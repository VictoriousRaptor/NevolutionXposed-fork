# 应用内回复与通知波次：静态评估（2026-11-06）

## 2026-11-13 后续重构说明

本文下方分析的是旧发送状态与回复分组实现，相关缺口已由新的产品规则替代：通知栏发送动作即结束，不监听微信发送/入库，不恢复本人跨轮正文；本机及多端同步已读由独立会话已读 hook 捕获。当前行为以通知历史策略及适配手册 2026-11-13 章节为准，不将历史探针或设备结果作为本次重构的验收。

## 最终结论与实现状态

本分支已完成源码修复和主机验证。最直接的根因是旧状态回调沿用了微信 SendMsgSuccessEvent 的分类排除：8.0.79 的 `a3(): boolean` 包含普通文字，导致应用内文字 B 在更新为状态 2 后仍被跳过。该问题不要求回调晚于 C；C 晚几十分钟也可能继续显示 ACD。回调是状态 setter 执行后的观察，不是对端已读或回复通知。

现已移除这组事件过滤，保留完整签名指纹和本人方向/状态/身份校验。以新来信代次建立波次，C/D 同时间或回退时间均可留在当前波次并按代次排序；旧波次不因保留回复设置恢复。精确 8.0.79/3182、3183、3200 可选读取 B 的文字或媒体占位，关闭设置显示 CD，开启显示 BCD；连续回复沿用整组。正文能力失败不阻止发送边界。

晚到回调是另一个边界问题：仅在归档时间和代次都能严格分隔旧/新来信时补设边界；记录当前波次已确认的前后时间，使连续迟到 B1/B2 能在 A 已裁剪、Parcel 往返后继续追加。顺序不明时不猜测删除。没有归档或尚未关联会话时不缓存正文等待恢复；同会话通知栏发送预留仍有既有竞争限制，这些保守行为已写入适配手册。

独立只读审查提出的同时间 D 丢失、连续迟到回复组丢失两项均已补主机失败回归并修复。最终 `testDebugUnitTest` 为 **327 项、0 失败、0 跳过**；`assembleDebug`、`assembleDebugAndroidTest` 通过，均使用 `-PrequireReleaseSigning=true`，APK 与现有 release 密钥证书一致，zipalign 检查通过。Android Bundle/通知框架用例只编译，未在手机执行；未安装本分支 APK、未重启进程或设备、未提交或推送。

用户随后授权了只读手机日志检查：近两小时没有可还原该链路的诊断，当前安装包为非 Debug 构建，旧 logcat 部分已覆盖。这既不能证实也不能否定本次 hook 路径。原始设备材料仅保存在本地忽略目录。本节以下保留首次静态分析的基线记录，旧行为描述不代表当前分支实现。

## 范围与目标

基线为 `f4c36b0`，分析分支 `codex/conversation-wave-analysis`。首次分析阶段只做源码分析和无需 Android 的本地探针；后续实施及用户授权日志检查见上方最终状态。

目标序列为对方 A、本人应用内 B、对方 C、D。关闭保留回复时依次展示 C、CD；开启时展示 BC、BCD。C 是当前波次固定起点，D 只追加。暂沿用连续本人回复整组保留的现有语义，此项是实现建议，尚无用户对单条/整组的明确选择。

## 基线链路与事实

1. `WeChatAppReplyEvents` 在微信主进程安装消息状态 setter AFTER hook；参数与更新后状态均为 2，本人方向为 1，排除项均为 false，ID/时间/talker 有效才发送事件。事件只有 talker、ID、创建时间，没有正文。
2. `WeChatDecorator.Local.onAppSent` 通过 `NotificationReplyOrigins` 去重和排除通知栏回复，再用 `ConversationManager.idsForTalker` 匹配已知会话，要求存在规范化归档及匹配身份。
3. `NotificationMessages.markAppReply` 更新归档 ROUND；`ConversationRound.appReply` 拒绝创建时间不大于 latestPeerTime 的事件。已接收事件保存 pendingAppReply 及归档 token。
4. 新原始通知经 `NotificationMessages.rebuild` 合并时调用 `incoming`；只有严格更新的非零时间才能推进。已规范化快照不推进。推进后按 cutoff 和 appReplyToken 清理旧来信，再按开关保留本人回复。
5. `incoming` 使用来信时间来自 `Notification.when`；应用内发送使用消息 `getCreateTime()`。二者不应未经验证就等同为可靠消息序列。
6. 应用内 B 未进入本人消息列表，所以现有开关不能展示 B。通知栏回复独立保存正文与回复 UUID。
7. 精确画像要求版本名与代码同时匹配并通过完整签名校验；同名未知代码仅唯一候选签名通过时实验启用，失败或歧义不装 hook。应用内回复能力不由合成回复/图片画像成功保证。

## 已复现的状态边界

使用原始 `ConversationRound.java`、`NotificationReplyOrigins.java` 与忽略目录中的 `WaveAnalysisProbe.java` 直接 javac/java 执行，7 项断言通过。这些断言确认当前行为（包含问题），不是修复通过。

| 输入条件 | 当前行为 | 影响 |
| --- | --- | --- |
| A=100，B=150 的回调先于 C=200，D=300 | A 被清理，C 保留至 D | 理想路径正确 |
| 先处理 A=100、C=200，后收到 B=150 的成功回调，再处理 D=300 | B 被拒绝；A 继续被保留 | 可形成 ACD；仅确认条件成立时的代码结果 |
| 已标记 B，C 的通知时间与 A 相同 | C 不推进轮次，A 保留 | 同时间通知无法及时切轮 |
| 已标记 B，C 的通知时间为 0 | C 不推进轮次，A 保留 | 单独应用内路径不保证无时间来信切轮 |
| 同会话存在通知栏发送预留，下一条事件来自应用内 | classify 返回 NOTIFICATION | 来源依赖会话与 120 秒窗口，缺少发送 ID 绑定 |

同时间/无时间 C 之后的 D 是否再次裁掉 C，还取决于消息轮次元数据及合并过程，不能用纯状态探针声称已覆盖。必须增加 Android Bundle 层回归。

其他静态风险：talker 尚未解析、没有规范化归档时，发送事件不缓存重放；`matched=0` 不能区分这些原因。模块关闭或事件门禁失败同样不会建立边界。上述条件是否出现在用户设备尚未验证。

## 现有测试覆盖缺口

`ConversationRoundTest` 将晚到应用内事件拒绝作为既有预期；这是需重新设计的行为，而非删掉判断即可修复。`MessageIdentityInstrumentation.appReplyStartsFresh` 直接调用 markAppReply，绕过 hook、来源分类和会话关联，仅验证顺序理想路径。现有测试不能证明真实发送链路可靠。

## 建议的实施顺序

1. 将显示波次与微信已读状态分开；先补全匿名诊断，区分版本门禁、事件筛选、来源分类、会话匹配和轮次拒绝。不得记录正文、talker、ID 或设备标识。
2. 建立能处理晚到事件的会话边界。发送事件的创建时间和通知接收代次不能简单互换：晚到 B 不得以当前归档 token 裁掉 C/D，也不能接受所有旧回调。应保存有界会话事件与消息归属，用已确认的发送/来信身份和顺序关联；无法排序的事件保守处理并诊断。
3. 对已确认在发送后到达的原始新来信，以代次/身份推进；相同或零通知时间不能单独阻止推进。旧快照、补图、撤回提示不能伪装新来信。
4. 独立核对正文能力：逐版本确认内容与消息类型访问器，正文不可读时仍允许既有发送边界工作；普通文字与媒体占位采用明确映射，不直接展示媒体 XML。不以正文猜测会话或发送来源。
5. 将可用 B 作为可选上下文附在 C 之前，保持去重、容量、移除和撤回边界；整组保留暂为建议。关闭开关不能阻止切轮，开启不能复活清理过的会话。
6. 同步通知历史策略、适配指南、受影响版本 findings；执行主机测试与签名构建，设备可用后另验真实发送、已读数和通知显示。
