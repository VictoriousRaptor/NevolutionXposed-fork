## 目标与已确认范围

- 改善展开通知中图片尤其是文字截图的可读性，避免低质量选图和过度降采样。
- 高清文件尚未就绪时，最多使用现有约 5 秒解析窗口等待本地高清图片，超时后降级到最佳有效本地图片。
- 不主动下载原图、不扫描目录，只使用与消息事件明确关联的文件。
- 只修共享选图、解码和相关缓存逻辑；微信 8.0.78 图片事件适配另行处理，现有版本门禁继续保留。

## 已核实的代码依据

- `WeChatImageEvents` 先收集普通缩略图路径，再收集高清缩略图路径。
- `ImagePreviewLoader.resolve()` 按路径顺序选择首个可解码文件；成功后立即发布，不再等待后续高清文件。
- 当前采样循环将宽高都限制在约 384px，并使用 `RGB_565`。二次幂采样可能进一步降低实际输出尺寸。
- `ImageEventIndex` 会合并同一消息的新旧路径，并将候选数量限制为 4；选择策略必须覆盖事件到达顺序和候选合并场景。
- 图片事件钩子仅支持微信 8.0.72/3085。8.0.78/3180 的既有适配是回复链路，不能据此宣称图片事件已经支持。
- 以上是静态代码证据。实际源图片尺寸及系统最终渲染损失仍需通过 Debug 日志和真机对照确认。

## 实现方案

### 候选选择与等待

- 检查全部消息关联候选的有效性和图片尺寸，不再采用首个可读路径。候选顺序不得决定清晰度。
- 优先选择能在不放大的情况下覆盖目标显示尺寸的图片；其余候选按可用分辨率选择最佳者。
- 候选达到目标显示要求时立即发布；否则在现有约 5 秒窗口内重新检查事件合并及文件落盘情况，到期后使用最佳有效图片。
- 没有有效图片时保留原通知。继续保留消息归属、通知令牌、请求取消及文件解码前后大小和修改时间检查。
- 将候选评分、等待判定及采样计算提取为包内纯逻辑，供单元测试调用；不增加公开 API。

### 解码与显示

- 优先根据系统 BigPicture 显示范围确定目标尺寸；无法读取时，以屏幕宽度和半屏高度作为后备。
- 单图硬上限为 1,048,576 像素，`ARGB_8888` 像素数据约 4 MiB；不得将此内存预算视为 Binder 传输必然安全的保证。
- 使用 `ARGB_8888`，计算不低于目标所需分辨率的最大安全 `inSampleSize`，再通过带过滤的等比缩放精确压入目标范围。
- 禁止放大小图，避免额外有损压缩；超出预算的图片在后台受控缩小。
- 保留 BigPicture 通知的回复动作、原始意图、通知令牌及仅提醒一次行为，并验证系统构建通知后的实际图片尺寸。

### 缓存与诊断

- 继续限制缓存数量为 4，并按实际位图字节数及 30 秒 TTL 清理；单图预算下总缓存像素数据最多约 16 MiB。
- 明确缓存、待发布任务和重挂操作的位图所有权，避免回收仍被使用的位图；对取消、失败和过期路径及时释放引用。
- 仅在 Debug 记录候选源尺寸、采样率、输出尺寸和字节数、等待时间及降级原因；不要新增完整私有路径或消息内容日志。
