# 微信应用内回复后的通知轮次方案

更新日期：2026-09-27

状态：源码已实现；8.0.72 / 3085 与 8.0.78 / 3180 的离线映射已核对，实际微信运行时行为待验证

## 问题与现有证据

复现场景：对方来信 A → 用户在微信 App 内回复 B → 对方再次来信 C。期望下一次通知从 C 开始新的展示轮次；当前通知可能继续合并 A 和更早的历史，逐轮变长。

- `NotificationMessages.recordReply()` 只在模块的通知回复回调中调用，负责保存带 `REPLY_ID` 的本人消息，并通过 `ConversationRound.reply()` 标记待推进轮次。
- `WeChatAppReplyEvents` 在已核对的微信版本上观察本人消息状态更新，只读取会话标识、消息 ID 与时间；不读取或保存应用内回复正文。`NotificationReplyOrigins` 排除由模块通知回复触发的发送事件。
- `ConversationRound.incoming()` 仅在出现严格更新的对方消息时间时提交应用内回复边界，并裁剪上一轮展示内容。通知历史最多保留 25 条仍是独立的上限。
- SystemUI 的通知移除广播只处理指定的移除原因；应用内发送不等价于点击、划除或清除全部。仅扩大到 `REASON_APP_CANCEL` 也无法证明用户确实发送了消息，并可能把阅读或普通通知更新误判为轮次结束。
- `WeChatImageEvents` 已能在 8.0.72 的部分消息路径读取 talker 和发送方向，但只在图片预览开启时安装，且有图片类型及版本门禁；不能直接拿来作为通用发送信号。
- 已保存的 8.0.72 / 3085 反编译源码中，`com.tencent.mm.storage.f9.q1(int): void` 先更新消息状态；本人消息（`C0() == 1`）处于状态 `M0() == 2` 时构造 `SendMsgSuccessEvent`。8.0.78 / 3180 的对应入口为 `com.tencent.mm.storage.e9.t1(int): void`。两版都已做精确版本与方法签名门禁。入口相对持久化和真实送达的时序仍待运行验证；该分支排除部分消息类型，不能据此承诺覆盖所有媒体发送。

以上版本映射来自离线源码核对，尚未用本次场景的隐私安全事件日志核对微信的实际通知更新时序。

## 推荐方案：已确认发送事件驱动轮次边界

### 1. 事件来源与版本门禁

1. 已核对 8.0.72 和 8.0.78 的完整类名、方法参数、返回类型和消息字段，并在状态更新后观察状态 2 的本人消息。真实设备上的事件时序仍待核对。
2. 只提取 `talker`、发送方向、消息类型、匿名消息 ID 与时间。正文、昵称、账号 ID 和完整 Intent 不进入日志或轮次状态。
3. 只接受 8.0.72 / 3085 和 8.0.78 / 3180；其他版本和签名不匹配时不安装该功能，维持现有通知行为。该钩子独立于图片预览开关。
4. 用只记录匿名阶段的诊断核对 A → App 内 B → C 时的发送事件、通知取消或更新原因、通知 ID 和轮次 token；确认回调只发生一次且能关联到正确会话。

### 2. 保存会话边界

1. 将已确认的本人发送事件按稳定 `talker` 关联到当前通知会话。`talker` 尚未解析、通知 ID 已复用或会话身份不一致时不猜测标题，也不清理其他会话。
2. 在发送事件到达时给该会话标记“待开始新轮次”，并清理该边界之前的待显示回复状态；连续多条 App 内发送只形成一个边界。以匿名消息 ID 去重，并使事件处理与通知重建有确定的先后顺序。
3. 不在发送瞬间重发或取消通知。只有下一条**严格更新**的对方消息到来，才由 `ConversationRound` 提交边界：丢弃旧对方消息和边界前的通知回复；保留边界后通过通知栏发出的回复以及新的对方消息。App 内回复正文不补入通知。
4. 边界随当前通知的轮次元数据保留，在图片预览重建中继续复制；通知被移除、会话切换或 ID 被复用时失效。微信进程重启后归档本已清空，不需要恢复旧边界。
5. 裁剪 `EXTRA_MESSAGES` 时同步更新 `EXTRA_REMOTE_INPUT_HISTORY`，避免显示已缩短但回复历史仍携带旧内容。

目标显示：A → App 内 B → C 时显示 C；A → App 内 B → 通知栏回复 D → E 时显示 D、E；纯通知栏回复继续沿用现有 A → B → C 显示 B、C 的规则。

## 不采用的捷径

- **只按 `REASON_APP_CANCEL` 重置**：通知取消不能唯一证明已发送，而且可能在新通知更新后才到达；现有 token 只能防止清错代次，不能证明发送事实。
- **仅缩小 25 条上限或按固定时间截断**：可缓解长度，但会丢失仍属于当前轮次的消息，且不能保证新轮次从正确位置开始。
- **直接清空全部通知归档**：异步通知、图片重建和同 ID 会话切换可能交错，必须先验证 talker 与通知代次。

## 验收与未决项

- 已完成：95 个单元测试通过，`assembleDebugAndroidTest` 构建通过，`lintDebug` 通过；尚未执行设备仪器测试或安装 APK。
- 纯逻辑与仪器测试：单聊、群聊、多会话交错、连续 App 内发送、重复发送回调、失败发送、旧或零时间来信、同文消息、通知 ID 复用、图片重建、通知移除，以及 App 内发送与通知栏回复交错。
- 运行验证：在实际目标微信版本上核对发送事件只在确认发送后出现、会话关联正确、下一次通知不带旧历史，且通知栏回复和回复动作未退化。仅构建测试 APK 不能证明微信混淆方法的运行行为。
- 未决项：真实微信运行时的钩子触发时序、消息时间与通知时间的对应关系、发送失败时是否产生相同事件，以及同一会话应用内发送与通知回复高度并发时的事件归属。源码实现已完成，仍需在获准的实际运行场景中核对这些行为。
